# Decisions

## D1 — Shape: one turn, three components
- A turn is: the user speaks a question, the assistant answers aloud. Push-to-talk, one utterance in and one out. No barge-in, no streaming audio in either direction, no conversation memory yet.
- Three components with one job each: speech to text, the answer (an LLM), text to speech. In M1 they run in one Python process on the laptop to prove the models and measure them. From M2 each is a service, so that on Kubernetes they scale and fail separately.
- Same rule as the earlier projects: the code that runs on the laptop is the code that runs in a container and on AKS; only configuration differs (D7).

## D2 — Speech to text: faster-whisper, Whisper small to start
- faster-whisper 1.2.1 (Whisper on CTranslate2 4.x), CPU, weights quantised to int8 at load. No GPU in the lab or on the planned AKS nodes.
- Model for M1: **Whisper small** (`Systran/faster-whisper-small`). Whisper pads every utterance to a 30-second window, so recognition time is nearly constant per utterance and is set by the encoder size. small keeps a turn interactive on a laptop CPU. `large-v3-turbo` is in the catalog for comparison; the choice between them is made on real speech (accuracy) against the time measured here, not on the synthetic round trip (D8). Chosen on real speech in M3: D16.
- Decoding: language fixed to Arabic (D5), beam 5, voice-activity filter on (silence is removed before recognition; Whisper invents text for non-speech), no conditioning on previous text (utterances are independent).
- The model directory must contain `model.bin`, `config.json` and `tokenizer.json`; the wrapper checks this before loading, because faster-whisper would otherwise try to download a missing tokenizer from the Hugging Face Hub at run time.
- `av` (PyAV) is pinned below 19: faster-whisper 1.2.1 calls `av.open(metadata_errors=...)`, an argument PyAV 19 removed; with PyAV 19 every file transcription fails with a `TypeError`. Remove the pin when faster-whisper supports PyAV 19.

## D3 — Text to speech: Piper, voice ar_JO-kareem-medium
- piper-tts 1.8.0 (the maintained `OHF-Voice/piper1-gpl`; the original MIT `rhasspy/piper` is archived). A VITS voice on ONNX Runtime: about 0.07 seconds of CPU per second of speech on two cores, roughly 200 MB of memory.
- Voice: `ar_JO-kareem-medium` from `rhasspy/piper-voices`, 22.05 kHz, one speaker. Written Arabic normally has no short vowels; Piper restores them before phonemising (a libtashkeel model inside the piper-tts package, applied automatically for Arabic voices). Its mistakes are audible as wrong vowels.
- Licence boundary: piper-tts is GPL-3.0-or-later. Text to speech therefore becomes its own service and image (M2, M4), called over HTTP; the other components do not import Piper. In M1 the scripts import it directly. Piper is not the only GPL software in the images, though: M4 found GPL encoder libraries inside PyAV's wheel in the speech-to-text image (D23).
- The assistant's text is cleaned before synthesis (`clean_for_speech`): markdown, links, list markers and emoji are removed, because the voice would read or stumble over them.

## D4 — Model files are pinned artifacts, outside git and images
- Models are fetched by `scripts/fetch_models.py` into `models/` (gitignored). `src/voice/modelstore.py` holds the catalog (which repository, which files); `models.lock.json` (committed) holds, per model, the repository revision and the SHA-256 and size of every file.
- First fetch of a model: resolves the newest revision and writes the lock entry (trust on first use). Every later fetch, on any machine: downloads that revision, and fails if a file differs from the lock. `--verify` compares what is on disk; `--update NAME` moves the lock on purpose.
- Why a lock and not only a revision: the SHA-256 lets a container or an init job check its model files without calling the hub, and it detects a changed file on disk.
- Licences: the Whisper conversions are MIT. The voice's model card names no licence and points to its dataset repository. Until that is clear the voice is not copied into a public image or redistributed; it is downloaded from its publisher at deploy time.

## D5 — Arabic only
- Input language is fixed to Arabic for recognition: language detection on a two-second utterance is unreliable and costs time. Answers are requested in Modern Standard Arabic.
- Not handled: dialects are recognised as well as Whisper happens to, mixed Arabic and English is not tested, and digits and Latin words in answers are read by Piper's rules. Each needs real-speech measurements before it is worth designing for.

## D6 — The answer: any OpenAI-compatible endpoint
- One `openai` SDK client (as in ticket-triage-agent D3). Locally Ollama's `/v1`; on Azure the Azure OpenAI v1 endpoint. `CHAT_REASONING_EFFORT` switches the request to the shape reasoning models need (`reasoning_effort` + `max_completion_tokens`, no `temperature`); empty locally.
- Local model to start: `phi4-mini:3.8b` on Ollama 0.40.15, CPU (MIT, no thinking mode, 2.5 GB, already used in the ticket-triage lab). Its Arabic answer quality is not measured yet; the model is one environment variable (`CHAT_MODEL`), and the comparison with other small models belongs to the Arabic evaluation milestone. Chosen in M3: D17.
- System prompt in Arabic: answer only in Modern Standard Arabic, one or two short sentences, nothing a voice cannot read. Temperature 0.2, at most 160 output tokens. The turn script reports the share of Arabic letters in the answer, because answering in another language is a known failure of small models.

## D7 — Configuration from environment variables only
- `src/voice/settings.py` reads everything from the environment; the defaults are the laptop values (`MODELS_DIR=models`, `STT_MODEL`, `OPENAI_BASE_URL=http://127.0.0.1:11434/v1`, ...). No configuration files, no values in code paths.
- Recognition threads default to the **physical cores** among the CPUs the process may run on (its CPU affinity), capped at 8; `STT_THREADS` overrides. Hyper-threads of one core share its arithmetic units, so a second Whisper thread on the same core only adds contention: on the i7-9750H (6 cores, 12 CPUs) Whisper small took 1.78 s on 6 threads and 4.32 s on 8 for the same 3.2 s utterance. Changed in M3; until then the default was the logical CPUs capped at 8.
- Cores are counted from `/sys/devices/system/cpu/cpu*/topology/core_cpus_list` (older kernels: `thread_siblings_list`): CPUs with the same list share a core. Without those files every CPU counts as a core.
- In a container this follows CPU pinning (cpuset), not CPU limits (CFS quota): a pod limited to 2 CPUs on a 16-core node still sees 16 CPUs. The Helm chart (M5) therefore sets `STT_THREADS` to the pod's CPU request.

## D8 — The round trip is a smoke test, not an accuracy measure
- `scripts/roundtrip.py`: eight Arabic sentences (`eval/roundtrip.jsonl`) go text → Piper → WAV → faster-whisper → text and are scored against the original after normalisation (`voice.textnorm.normalize`: diacritics and punctuation removed, alef, ya and ta marbuta forms unified). Character error rate is counted without spaces; word error rate on whitespace-separated words.
- It proves that both models load, agree on audio format and understand each other, and it measures time per sentence on this machine. It does not measure recognition of real speakers: the audio is clean, synthetic and from one voice.
- Gates: corpus CER ≤ 10 %, corpus WER ≤ 20 %, no sentence above 30 % CER, and two seconds of silence must transcribe to nothing. When they were set, Whisper small scored 3.3 % CER and 8 % WER; Whisper tiny scored 6.5 % and 30 % and fails. The gate catches a broken pipeline or a much weaker model, nothing finer.
- Piper adds random noise to every synthesis. The script fixes ONNX Runtime's seed, so the audio and the result repeat on the same machine.

## D9 — One dependency group per image
- `pyproject.toml` has no base dependencies. Each image has a dependency group of its own and installs only that one: `stt` (FastAPI, uvicorn, python-multipart, faster-whisper, PyAV), `tts` (FastAPI, uvicorn, Piper), `gateway` (FastAPI, uvicorn, python-multipart, the OpenAI client), `models` (the hub client). `web` holds what the three services share and is included by them. On the laptop `uv sync` installs every group.
- So the speech-to-text image never contains Piper (D3), text to speech never contains CTranslate2, only the gateway has the OpenAI client, and only the fetch job downloads anything. `scripts/check_images.py` checks this on the built images (D19).
- Until M4 the web packages and the OpenAI client were base dependencies, which put them into every image, the fetch job included.

## D10 — Three services on OpenAI's routes
- `stt` serves `POST /v1/audio/transcriptions` (multipart `file`, `model`, `language`, `response_format` json|text → `{"text", "duration"}`), `tts` serves `POST /v1/audio/speech` (JSON `input`, `model`, `voice`, `response_format` wav → WAV bytes), the gateway serves `POST /api/turn` (multipart `file` → `{"heard", "answer", "audio", "timings"}`) and the push-to-talk page at `/`.
- Speaking OpenAI's shapes means the gateway needs one client library for all three steps, and a hosted service (Azure OpenAI's audio routes, Azure Speech behind an adapter) can replace a pod by changing `STT_URL`, `TTS_URL` or `OPENAI_BASE_URL`. Only what this project uses is implemented: `model` and `voice` are accepted and ignored (one model per process), other languages, formats and speeds are refused with 400.
- Only the `tts` process imports Piper (GPL, D3); the gateway reaches it over HTTP.
- The gateway returns the answer's audio as base64 inside the JSON (about 200 KB per answer) instead of streaming: one request per turn, simple to test. Streaming belongs with lower-latency work, not with this milestone.

## D11 — One model call at a time per process, a short queue, then 503
- A Whisper or Piper model uses all the CPU threads it is given, so two calls at once in one process only slow each other down. Each speech service runs one call at a time (`Worker`, off the event loop) and lets at most `MAX_WAITING` (4) requests wait; the next one gets 503 `busy` at once instead of a timeout minutes later.
- One request is one job (decode, length check, recognition together), so a full queue gives 503 and never a misleading 400.
- More capacity is more processes (replicas on Kubernetes), not more threads in one.

## D12 — Health: liveness and readiness only about the process itself
- `/healthz`: the process answers. `/readyz`: the model is loaded. Models load before the port opens (FastAPI lifespan), so a starting pod refuses connections until it can work: on Kubernetes that is a startup probe plus a readiness probe.
- The gateway's readiness does not check the speech services or the chat endpoint: a dependency being down would otherwise take the gateway out of the load balancer too, and the user would get a connection error instead of `503 stt_unavailable`. Each step's failure is named in the error code (`stt_`, `chat_`, `tts_` + `unavailable` | `busy` | `failed`).

## D13 — Limits, errors and logs
- Limits (environment variables): recording ≤ 2 MiB (`MAX_UPLOAD_BYTES`, checked by the gateway and again by `stt`), ≤ 20 s after decoding (`MAX_AUDIO_SECONDS`; the decoded length, so a small compressed file cannot carry an hour of audio), answer to speak ≤ 600 characters (`MAX_SPEECH_CHARS`; the gateway cuts a longer answer at a word boundary). The page stops recording at 15 s.
- Error bodies are OpenAI-style `{"error": {"code", "message"}}` with fixed messages; FastAPI's validation errors are replaced by a 400 that names the fields only (its default 422 echoes the submitted values). As in ticket-triage-agent, errors never echo input.
- Logs carry lengths and times only (`heard 28 chars, answered 31 chars, {'stt': 2.07, ...}`): what the user said and heard stays out of them. A unit test checks this.

## D14 — M2 runs as processes on the laptop; containers come in M4
- The milestone plan had `docker compose up` running everything in M2. That needs images, which are M4's subject (non-root, read-only, no models inside). M2 runs the three services with `uv run uvicorn` in three terminals; only Ollama is a container. M4 adds the images and moves all four into compose.
- Ports: `stt` 8001, `tts` 8002, gateway 8080, all on 127.0.0.1. The page needs a secure context for the microphone; `http://localhost` is one.
- Done in M4: D19 (images), D20 (models volume), D21 (compose). The three-terminal way still works for development (`docker compose up -d ollama`).

## D15 — Real-speech test sets: your recordings and FLEURS, audio outside git
- **own** (`eval/speech/own.jsonl`): 20 prompts read by Salman into his laptop microphone with Windows Sound Recorder — 14 in Modern Standard Arabic (questions an assistant gets: places in Bahrain, a date and time, numbers, a request) and 6 in Gulf dialect. This is the product's case: short questions, one speaker, a laptop microphone. The model choices (D16, D17) are made on it.
- **fleurs**: the first 40 sentences (lowest sentence id first, one recording each, at most 20 s) of the `ar_eg` test split of Google's FLEURS (`google/fleurs` on Hugging Face, CC BY 4.0: use with attribution). Read Wikipedia sentences in Modern Standard Arabic by Egyptian speakers: longer and harder than a voice question, and other voices than the developer's. Reported next to own, not used to choose.
- FLEURS recorded every sentence from three different native speakers and kept between zero and three of those recordings; the TSV names no speaker, and its gender column says FEMALE on all 428 rows of the ar_eg test split, so it cannot separate voices. The first build (M3) took the first recording of every sentence: always the same position, so "several speakers" was not shown. Since M4 the n-th sentence takes its (n mod k)-th usable recording, k being how many it has; the set was rebuilt on the same dataset revision and both FLEURS evaluations were run again. That spreads the set over recording positions, which within a sentence are different people; across sentences FLEURS says nothing about who is who. Checked by listening to F001 and F002 (M5 Step 0): . Only listening can show it; the metadata cannot.
- Common Voice Arabic was not used: since October 2025 it is only on the Mozilla Data Collective, behind an account and terms that forbid re-sharing. FLEURS needs neither.
- Audio is not committed (`data/` is gitignored): a public repository is no place for the developer's voice, and FLEURS stays with its publisher. `data/speech/<set>/manifest.jsonl` records reference, length and SHA-256 of every file; `scripts/speech_set.py status` checks the files against it. The prompts and the scripts that rebuild both sets are committed.
- Scoring is D8's: CER without spaces and WER after `voice.textnorm.normalize`. Limits of that: numbers spoken as words against digits in the reference count as errors, and dialect has no single spelling (the own references give one), so Gulf WER overstates the errors.
- Six utterances per style is enough to see a large gap between MSA and dialect, not a small one.

## D16 — Speech to text: `stt-small`
- Candidates: Whisper small and large-v3-turbo (D2), int8, beam 5, threads by D7, measured by `scripts/eval_stt.py` on both sets (D15).
- Rule (`voice.quality.choose_stt`): a model is eligible when its p90 time per utterance on the own set is within the speech-to-text budget (2.5 s, D18). Among eligible models the lowest own-set CER wins; a CER less than one point lower than a faster model's does not count (noise on 20 utterances). If no model is within budget, the fastest is chosen and the budget is reported as missed.
- Result: own-set CER 10.1% at p90 1.96 s, within the 2.5 s budget; over budget: stt-turbo p90 8.99 s. Numbers: `docs/evidence/m3-summary.md` and `m3-stt-*.md`.
- The chosen model is the `STT_MODEL` default in `settings.py`; the other stays in the catalog and the lock.

## D17 — Chat model on the laptop: `phi4-mini:3.8b`
- Candidates, all through Ollama 0.40.15 on CPU, one loaded at a time: `phi4-mini:3.8b` (MIT, the M1 start), `gemma3:4b` (Gemma terms, 140 languages, no thinking mode), `qwen3.5:4b` (Apache 2.0; thinks by default, run with thinking off), `command-r7b-arabic:7b` (Cohere's Arabic-tuned 7B, CC BY-NC 4.0: fine for this non-commercial lab, not for a product), optionally `gemma4:e2b` (Apache 2.0; Ollama's default tag is 7.2 GB, over the memory budget before measuring).
- Thinking models get `CHAT_REASONING_EFFORT=none`: `voice.llm.Assistant` then keeps the classic request (temperature, `max_tokens`) and adds `reasoning_effort: "none"`, which Ollama's `/v1` maps to thinking off. A voice turn cannot wait for a hidden reasoning pass, and thinking spends the 160-token limit before the answer.
- Test: `eval/qa.jsonl`, 24 Arabic questions with known answers (Bahrain and Gulf facts, world facts, numbers and arithmetic), asked once each with the product's own request (system prompt, temperature 0.2, 160 tokens) by `scripts/eval_chat.py`. Correct = an accepted answer appears as whole words after normalisation; Arabic = at least 90 % Arabic letters; memory = Ollama's resident size of the loaded model.
- Rule (`voice.quality.choose_chat`): eligible when every answer arrived, at least 95 % of answers are Arabic, the model fits in 7 GB, and its warm p90 is within the chat budget (3.5 s, D18). Most correct answers wins, then the faster p50. If none is within the time budget, the most correct one that fits in memory is chosen and the budget is reported as missed. Below 80 % correct the model is called what it is: a stand-in for development until Azure OpenAI (M8) answers on AKS.
- Result: 54% correct, 96% Arabic, p90 2.38 s, 3.1 GB; below the 80% correctness bar: a lab stand-in until Azure OpenAI (M8); ruled out: command-r7b-arabic:7b (p90 33.12 s), gemma3:4b (p90 5.34 s), qwen3.5:4b@none (p90 8.31 s). Numbers: `docs/evidence/m3-summary.md` and `m3-chat.md`.
- What the scoring misses (seen in `m3-chat.md`, noted in M4). (1) An answer counts as correct when an accepted form appears in it; a wrong fact next to it is not noticed (one qwen3.5 answer placed Bahrain on the Red Sea and counted). The correct rate is therefore an upper bound, and it says nothing about what else the model asserts. (2) The system prompt's last sentence, "if the question is unclear, ask the user to repeat it", made gemma3 and qwen3.5 answer Q20 ("how many hours are in a day?") with a request to repeat: scored wrong, but it is the prompt's doing, not missing knowledge, and it costs each of them one question of 24. The prompt was not changed for it: that would mean measuring all four models again, and the same clause is what the assistant should do with a mis-heard question.
- 24 questions measure gross differences (the capital of Bahrain, simple arithmetic, staying in Arabic), not general quality. The questions are a tuning set from now on: a later prompt change is checked against it, and any claim about held-out quality needs new questions.

## D18 — Time budget per stage
- Budget for one turn, warm, on the laptop, from the end of the question to the start of the answer audio, as p90 over the own set: speech to text 2.5 s, chat 3.5 s, text to speech 0.8 s, everything else (gateway, HTTP hops, base64) 0.2 s; **total 7 s**. Seven seconds is slow for a conversation but usable for push-to-talk questions on a CPU; the stage split shows where time goes when it is missed. Chat memory budget 7 GB, so the speech services and Windows still fit in 16 GB.
- Measured by `scripts/measure_turns.py`: every own recording through the running gateway, after one warm-up turn, with the chosen models. Result: p50 4.49 s / p90 6.84 s against 7 s; over: chat p90 3.61 s > 3.5 s (`stt-small` + `phi4-mini:3.8b`, 2026-11-16 15:48 UTC).
- Cold start is outside the budget and only reported: loading a chat model took up to a minute on this laptop in M3 and 2 min 36 s under compose's limit in M4. Since M5 Ollama loads the model before it counts as ready and keeps it for good (D25); the speech pods load theirs before they report ready (D12).
- The numbers carry into M5: CPU requests from the threads that met the budget, memory requests/limits from the peak resident memory `measure_turns.py` reports per service (with headroom), and the startup probe from the model load times.

## D19 — Images: one Dockerfile, four targets, nothing in them that the service does not need
- `Dockerfile` builds `stt`, `tts`, `gateway` and the model-fetch job `models`. Each gets a virtual environment of its own from its dependency group (D9), installed by uv with `--locked` (exactly `uv.lock`) in a build stage and copied into the runtime stage; the project is installed as a normal package (`--no-editable`), so there is no source tree, no uv and no build cache in an image. pip is removed from the runtime stage.
- Base: `python:3.13-slim-trixie` for both stages (the environment's interpreter path must be the same in both), uv from `ghcr.io/astral-sh/uv`. Both are pinned by digest in the Dockerfile's two `ARG` lines, as is Ollama in `docker-compose.yml`; `scripts/pin_images.py` resolves the tags and writes the digests, `--check` fails on an unpinned image. A tag can be moved by its publisher; a digest cannot.
- Official Python image and not a standalone Python build on a bare Debian image: its interpreter uses Debian's OpenSSL and zlib packages, which a scanner sees and Debian patches. A statically linked interpreter would hide them. Not distroless either: the health check and `docker exec … python` need the interpreter anyway, and the chart in M5 gets the same effect from a read-only filesystem and dropped capabilities.
- No model file is in any image (D4, D20). The build context is an allow-list (`.dockerignore`: `pyproject.toml`, `uv.lock`, `models.lock.json`, `src/`), so `models/`, the recordings in `data/`, `.env` and `.git` cannot reach an image whatever the Dockerfile copies.
- Runs as user `10001:10001`, a number and not a name (Kubernetes checks `runAsNonRoot` against a number). The image is built to run on a read-only root filesystem: bytecode is compiled at build time, `HOME` is `/tmp`, and the only writable place is a small memory-backed `/tmp` (uploads over 1 MB are spooled there). Read-only, dropped capabilities and `no-new-privileges` are set where the container is started (D21), because an image cannot enforce them.
- No `HEALTHCHECK` in the Dockerfile: Kubernetes ignores it, so compose (D21) and the chart (M5) each declare their own check on `/readyz`.
- Piper is only in `tts` (D3): that image carries the label `org.opencontainers.image.licenses=GPL-3.0-or-later`; see D23 for what that means for publishing.
- `scripts/check_images.py` checks the built images: configured user and real uid, no file with the name and size of a locked model file, `/models` empty, and the package rules of D9 (Piper only in `tts`, CTranslate2 only in `stt`, the OpenAI client only in `gateway`, the hub client only in `stt` and `models`, pip nowhere). Sizes and image ids: `docs/evidence/m4-images.md`.

## D20 — Models come from a volume, filled and checked by a job
- `python -m voice.fetch_job NAME …` (image `models`) runs to completion before the speech services start. It is the only component with a reason to reach the model host and the only writer of the `models` volume; `stt` and `tts` mount the volume read-only.
- The lock file is copied into the job's image, so an image digest fixes which model bytes it accepts. The job refuses a model that is not in the lock, never asks for "the newest revision" and never writes the lock: moving a model is done on a workstation with `scripts/fetch_models.py --update`, reviewed as a change to `models.lock.json`, then built into a new image.
- Per model: files the lock does not list are removed; if the directory then matches the lock (SHA-256 and size of every file) nothing is downloaded, so a start on a filled volume needs no network and costs a second or two of hashing; otherwise the locked revision is downloaded and compared. Any difference is exit status 1.
- The services refuse to start without their model: `SpeechToText` and `TextToSpeech` check their files before loading, the process exits with status 3, and nothing listens on the port. In compose the services also wait for the job (`service_completed_successfully`), so a failed check stops them from starting at all.
- Not done: the services do not hash the model again at start (the volume is read-only for them and the job has just checked it; hashing 484 MB on every start of every replica would cost seconds). A file changed on the volume between the job and a later restart of a service would not be noticed until the job runs again.
- Kubernetes (M5): the same image as a Job with the volume mounted read-write, and in `--check` mode as an init container of the speech pods (D24). That closes the gap above on Kubernetes: every pod start checks every file.

## D21 — Compose runs all four services
- `docker compose up -d --build --wait`: the fetch job, then `stt` and `tts` (each waits for the job to succeed), then the gateway (waits for `stt`, `tts` and Ollama to be healthy). The health checks call `/readyz` with the image's own Python (there is no curl in the image); a starting container is polled every 2 s for up to 60 s, a running one every 15 s.
- Every published port is bound to 127.0.0.1: gateway 8080, `stt` 8001, `tts` 8002, Ollama 11434. Inside the compose network the services listen on 8000 (`stt`, `tts`) and 8080 and find each other by name. Docker Desktop forwards 127.0.0.1 ports to Windows, so the push-to-talk page is `http://localhost:8080` in a Windows browser, still a secure context for the microphone.
- Our containers run as `10001:10001` with a read-only root filesystem, a 16 MB `/tmp` in memory, all capabilities dropped and `no-new-privileges`. Ollama runs as its publisher ships it (root, writable) in compose, where `docker exec … ollama pull` writes its volume; on Kubernetes it runs as 10001 on a read-only filesystem (D30).
- Memory limits: limit = the highest peak resident memory seen × 1.5, rounded up to a multiple of 128 MB, at least 256 MB. Peaks from M3's measurement through the services (D18), unless real use went higher: `stt` 1328 MB (M4, after push-to-talk turns from a browser; the 20 recordings alone peak at 881 MB, as in M3) → 2048 MB, `tts` 615 MB → 1024 MB, gateway 74 MB → 256 MB, Ollama 3.11 GB (phi4-mini) → 4480 MB. The first M4 limit for `stt` was 1408 MB, from M3's 878 MB, and real use reached 94 % of it: a limit from an evaluation set alone is not enough. Swap is set equal to the limit: a service that needs more is killed and restarted, visibly, instead of slowing every turn down. Together 7.6 GiB of the 12 GB WSL has. A larger chat model (`command-r7b-arabic`, 5.6 GB) does not fit Ollama's limit: raise it in the same change. The fetch job has 512 MB (measured only against a stand-in model host).
- M3's peaks are the processes' resident memory; a container's limit also counts its `/tmp` and the page cache of files it read (the cache is given back under pressure). `scripts/measure_turns.py --compose` therefore reports each service's own peak (as in M3) next to its limit.
- `STT_THREADS` is set in the compose file (6, the i7-9750H's cores; `.env` overrides): a container sees every CPU of the machine whatever its limits (D7). No CPU limits: on a laptop they would only slow the one request there is. Requests and limits on Kubernetes: D26.
- No network separation between the services, and no egress block for `stt`, `tts` and the gateway: compose's `internal` networks cannot publish ports. Default-deny NetworkPolicy on Kubernetes: D29.
- A turn through compose against the budget (D18): `docs/evidence/m4-turns.md`. The same 20 turns on the same containers gave total p90 5.86 s on one run and 7.32 s on the next (`stt` p90 2.29 s and 3.69 s): on this laptop the tail of one run moves by more than a second with whatever else is running, so the evidence is a run on an otherwise idle machine, and a single run over or under the budget is not a verdict.
- One turn (S19) failed with `tts_unavailable` (the gateway could not reach `tts`) in the first measurement and not in the re-run; the containers were removed before they could be inspected, so the cause is not known. If it recurs: `docker inspect voice-tts --format '{{.RestartCount}} {{.State.OOMKilled}}'` and `docker events --filter event=oom --filter event=die` before anything is stopped.
- `stt` and `tts` exited with 137 on `docker compose down` in M4: they did not stop within Docker's 10 s grace period and were killed. Looked at and bounded in M5: D31.

## D22 — Scanning and pins
- Gate: `trivy image --scanners vuln --ignore-unfixed --severity HIGH,CRITICAL --exit-code 1` on each of the four images: no High or Critical vulnerability for which a fixed version exists, in Debian packages or in Python packages. Unfixed findings are counted and reported, not gated: nothing can be done about them but wait or change base.
- Trivy 0.76.2 as a binary from its GitHub release, checked against the release's SHA-256 before it is unpacked, and not as a container with the Docker socket mounted. Trivy's releases and actions were compromised in March 2026 (a malicious 0.69.4); a pinned version and a checked download are the minimum. The checksum comes from the same place as the binary, so it catches a corrupted or swapped file, not a compromised release.
- When the gate fails: a Debian package → `scripts/pin_images.py` (newest digest of the same tag), rebuild, scan; if the base has not been rebuilt with the fix yet, the runtime stage installs the fixed version of that one package, by exact version (a blanket `apt-get upgrade` would make every build depend on its date), with a comment saying when to remove it; a Python package → `uv lock --upgrade-package <name>`, tests, rebuild, scan. An exception (`.trivyignore`) needs a line here with the reason and a date to look again.
- The pins age: a digest never changes, so fixes do not arrive by themselves. From M6, CI scans on a schedule and Dependabot proposes new digests.
- Ollama's image is pinned but not scanned or gated here: it is not ours to rebuild.
- First run (2026-11-16): all four images failed on the same two High findings in `zlib1g` `1:1.3.dfsg+really1.3.1-1+b1`, from the base image, fixed in Debian's security update `…-1+deb13u1`; nothing in our own layers was flagged. The base had not been rebuilt with it, so the runtime stage installs `zlib1g=1:1.3.dfsg+really1.3.1-1+deb13u1`. Remove that line when `scripts/pin_images.py` moves the base to a digest whose `dpkg-query -W zlib1g` already shows `+deb13u1` or later (check on every re-pin).
- Results: `docs/evidence/m4-trivy-*.txt`; image ids: `docs/evidence/m4-images.md`.

## D23 — Registry: GitHub Container Registry for what CI builds; Azure Container Registry only as the cluster's copy
- Nothing is pushed in M4: compose builds locally, and minikube (M5) can load local images. The first push is CI's (M6), so that what runs on a cluster was built from a commit and not from a laptop.
- Build registry: **GHCR** (`ghcr.io/salmanamn/…`), public packages. Free for public images, anonymous pulls (minikube, a reader of the repository), pushes from GitHub Actions with the job's own token, and the images survive the Azure stack, which is destroyed after every session. An Azure registry as the only registry would have to live in a persistent resource group and be paid for every day to hold four images.
- For AKS (M7/M8) the plan is an ACR Basic created with the stack, filled by `az acr import` from GHCR **by digest**, and pulled by the kubelet identity with `AcrPull`: pulls by managed identity, no pull secret, no dependence on GHCR's rate limit per outbound address, and a policy "only images from our registry" becomes possible (Project 7). Pulling straight from GHCR would also work for public images; M7 decides when the Terraform for the cluster is written. (`az acr import` and not artifact cache: Microsoft's pages disagree on whether cache rules exist in the Basic tier.)
- Open before the first public push, and the owner's call: **the licence.** The repository has no licence file, and two images redistribute GPL software. `tts` contains Piper (GPL-3.0-or-later) together with this project's `tts` service, which imports it. `stt` contains PyAV's wheel, which is BSD itself but bundles FFmpeg (built as LGPL v3) and the x264 and x265 encoder libraries (GPL): found in M4 by listing `av.libs`, and not what D3 assumed when it called Piper the only GPL part. Publishing either image means distributing those works under their terms (notices, an offer of source), and for `tts` the project's own code in it has to be under a GPL-compatible licence. `gateway` and `models` contain only MIT, BSD and Apache packages. Until a licence is chosen and the notices are in place, `stt` and `tts` are not pushed as public packages; private packages or the Azure registry do not distribute to the public. Not legal advice.
- Model files are never in an image (D4), so the voice's unclear licence does not touch the registry question.

## D24 — Speech models on Kubernetes: a Job writes the volume, every pod checks it
- The `models` image runs as a Job (`models-<hash>`) with the `models` volume read-write: the only pod that writes it and the only one allowed to reach the model host (D29). Not an init container of the speech pods: a pod's NetworkPolicy covers all its containers, so an init container that downloads would give `stt` and `tts` the same way out, and every replica would hold write access to the shared volume.
- The Job's name carries a hash of its image, model list and model host, because a Job's pod template cannot be changed: a new model list or image is a new Job, and Helm deletes the old one. An unchanged release keeps the completed Job and does not run it again.
- `stt` and `tts` start with an init container from the same image: `python -m voice.fetch_job --check <model>`, read-only volume, no network. `--check` compares every file with the lock (SHA-256 and size) and changes nothing; until the Job has finished it fails and the init container tries again every 5 s, so a new pod waits for the Job instead of crash-looping. On every later start (a restart, a replica the autoscaler adds) it hashes the files again, which D20 left undone in compose: a few seconds per start for 486 MB, against a pod that would otherwise run on whatever is on the volume.
- `ReadWriteOnce` volumes: the Job and the readers share one minikube node. On AKS (M7) a disk attaches to one node at a time, so the readers either share a node or the volume becomes Azure Files (`ReadOnlyMany`). The volumes have `helm.sh/resource-policy: keep`: `helm uninstall` leaves the downloaded models; deleting them is a separate, deliberate `kubectl delete pvc`.

## D25 — The chat model: pulled by a Job, pinned by id, loaded before Ollama is ready
- **Cold load against the gateway's 120 s chat timeout** (M4: 2 min 36 s, so the first turn after an Ollama restart failed with `503 chat_unavailable`). Chosen: Ollama is not ready until the model is in memory, and the model then stays there. A longer first-call timeout was rejected: the user would wait minutes for the first answer instead of getting an immediate, named error. A warm-up step in the start routine was rejected: it is one more thing to forget, and it does nothing after a restart nobody saw.
- One script for both places, `deploy/charts/voice/files/ollama-model.sh`, using only bash and the `ollama` binary (the Ollama image has no curl and no Python). `load` sends Ollama's documented preload request (`/api/generate` with the model and no prompt, `keep_alive: -1`) and succeeds once it returns; `check` succeeds when `/api/ps` lists the model. On Kubernetes `load` is the startup probe (timeout 300 s, three attempts) and `check` the readiness probe, so the `ollama` Service has no endpoint while the model loads and the gateway answers `503 chat_unavailable` at once. In compose `load` is the health check (timeout 300 s, start period 300 s) and the gateway waits for it, so `docker compose up --wait` returns with the model loaded. `OLLAMA_KEEP_ALIVE=-1` in both: the container exists to hold this one model, and its memory limit is sized for it.
- The 4480 MB limit and the load time: three loads in recreated containers (`scripts/measure_ollama_load.sh`, `docs/evidence/m5-ollama-load.md`): with the limit and the model file not yet in the host's page cache, with the limit and the file cached, and with 8 GiB and the file cached. The limit stays: a slow load now costs start-up time and never a failed turn.
- On Kubernetes a Job (`ollama-pull-<hash>`, Ollama's image) starts a private server on the `ollama-models` volume, pulls `ollama.model` unless it is there, and fails unless `ollama list` shows the id in `ollama.modelId` (values.yaml): Ollama tags move, so the id plays the part `models.lock.json` plays for the speech models. The Ollama Deployment waits for that id in an init container (`verify`), mounts the volume read-only and never needs the registry. `Recreate` strategy: two Ollama pods would need two copies of the model in memory.
- `OLLAMA_NO_CLOUD=1` everywhere: Ollama 0.40 otherwise calls ollama.com at start (cloud models, recommendations), which the policies would block anyway (D29).

## D26 — Requests and limits
- Memory request = the highest peak resident memory seen (D21), rounded up to 128 MiB; limit = D21's compose limit (peak × 1.5): `stt` 1408 / 2048 MiB, `tts` 640 / 1024, gateway 128 / 256, Ollama 3072 / 4480, fetch job 512 / 512. A request at the peak keeps the scheduler from packing more onto the node than really fits; the limit catches a leak or an unexpected model as a visible OOM kill instead of slowness.
- CPU: requests only, no limits. A CPU limit throttles a pod in 100 ms slices even when the node is idle, which is extra latency for the one call a speech service runs at a time (D11); a request reserves CPU and weights sharing under contention. `stt` requests 3 CPUs and gets `STT_THREADS` from its own request through the downward API (`resourceFieldRef requests.cpu`, divisor 1, rounded up), so the two cannot drift apart (D7). Three, not six: two replicas then use the laptop's six cores, and a single turn is slower than compose's six threads (measured in M5 Step 6). `tts` 1 CPU, gateway 250m, Ollama 2 (Ollama picks its own thread count; the request is for scheduling).
- minikube gets 12 CPUs and 10 GiB, the most the 16 GB laptop can give next to Windows and Docker Desktop, with compose stopped: the requests above (two `stt` replicas) come to about 6.5 GiB, the limits to 9.6 GiB.

## D27 — The gateway opens a new connection for every speech call
- A Service spreads connections over its pods, not requests. With keep-alive, the gateway's few connections to `stt` stay with the replicas they were opened to, and a replica the autoscaler adds gets nothing from a busy gateway. The `stt` and `tts` clients therefore keep no idle connection (`max_keepalive_connections=0`); one more TCP handshake inside the cluster costs about a millisecond against seconds of model work. A unit test checks that three turns are three connections to each service.
- `httpx2` (the HTTP client the `openai` SDK uses since 3.x) is now listed in the gateway's dependency group: the gateway constructs its connection limits itself.

## D28 — Autoscaling `stt` on CPU
- `stt` is the stage whose time grows with load; `tts` is short per call and Ollama holds one model per pod (a replica would need another 4.4 GiB). The HorizontalPodAutoscaler scales `stt` between 1 and 2 replicas on CPU utilisation, target 60 % of the request.
- What one call at a time (D11) means for that target: with `STT_THREADS` equal to the request, a replica working on a call uses about 100 % of its request and an idle one about 0 %, so utilisation is the share of the last minute the replica was busy. 60 % means "busy more than 60 % of the time" (callers have started to queue behind each other). Utilisation cannot go above about 100 %, so one step adds at most 100/60 of the current replicas (one more, here), and the queue length, which says more about waiting callers, is invisible to it. A queue-length metric needs a custom-metrics adapter (Prometheus or KEDA): considered for AKS, not on the laptop.
- Two replicas is the laptop's ceiling (memory and six cores). Scale-down waits 120 s (default 300 s) so the demo shows it.
- Shown with an in-cluster load test (`loadtest.enabled=true`: four workers send the same spoken question to `stt` for four minutes, each call on a new connection): `docs/evidence/m5-hpa.md`.

## D29 — Network: everything denied, then the flows a turn needs
- `default-deny` selects every pod in the namespace, ingress and egress. Then: gateway → `stt`/`tts` :8000 and Ollama :11434, plus DNS; `stt`, `tts`, Ollama: ingress from the gateway only (and from the test pods), no egress at all, not even DNS; the two download Jobs: DNS and the model hosts, no ingress; the `helm test` pod: gateway and `tts` (it has `tts` speak its question); the load test: `stt` and `tts`.
- NetworkPolicy has no host names, only addresses. The model hosts (Hugging Face and its CDN, Ollama's registry) are therefore "public addresses on 443": `0.0.0.0/0` minus the private, carrier-grade NAT, link-local and loopback ranges. That stops the Jobs reaching anything inside the cluster or the laptop's networks, not a public host other than the model hosts. Allowing names needs a CNI with FQDN policies (Cilium on AKS, or an egress firewall): M7.
- Not filtered by design: kubelet probes (NetworkPolicy always allows a pod's own node) and `kubectl port-forward` (it connects inside the pod's network namespace); the browser reaches the gateway through the latter.
- `scripts/check_netpol.py` connects from inside every pod, and from short-lived probe pods with the labels of the Jobs, the test pods and an unknown component, to every Service by cluster IP and to one address outside: 44 flows, each expected open or closed. `docs/evidence/m5-netpol.md`. Calico enforces the policies on minikube (`--cni=calico`).

## D30 — Restricted Pod Security Standard, Ollama included
- `deploy/namespace.yaml` labels the namespace `pod-security.kubernetes.io/enforce=restricted` (and `warn`, `audit`), pinned to `v1.37` so a cluster upgrade cannot change the policy unnoticed. Every pod of the chart: `runAsNonRoot`, uid/gid 10001, `seccompProfile: RuntimeDefault`, no service-account token; every container: `allowPrivilegeEscalation: false`, read-only root filesystem, all capabilities dropped, a 16 MiB in-memory `/tmp`.
- Ollama, which runs as root in compose: here uid 10001, `HOME=/tmp` (it writes its key there), models from `OLLAMA_MODELS=/models`, read-only, `OLLAMA_NOPRUNE=1` (pruning would write). Ollama 0.40.15 stores manifests in `manifests-v2/` but still creates `manifests/` at start and fails on a read-only volume without it, so the pull Job creates that directory. Found and tested in M5 with the 0.40.15 release binary as uid 10001 on a read-only filesystem; the image itself is Docker Hub's, not rebuilt.
- A pod that breaks the standard is refused at admission (checked with a root pod in Step 2); `kubectl label --dry-run=server` against the namespace lists running pods that would violate it (none).

## D31 — Stopping: drain, then exit, within a bounded time
- Under M4, `stt` and `tts` were killed after Docker's 10 s on `docker compose down`. M5 Step 0 recorded, on the M4 images, how long each took from SIGTERM to exit and which shutdown phase it was in (`scripts/check_stop.py`, `docs/evidence/m5-stop.md`).
- The stop is now bounded on both sides. uvicorn runs with `--timeout-graceful-shutdown 30`: on SIGTERM it stops accepting, finishes the call in progress and the ones queued behind it (D11), and gives up on what is left after 30 s. Compose waits 45 s before SIGKILL (`stop_grace_period`), Kubernetes too (`terminationGracePeriodSeconds: 45`). On Kubernetes a `preStop` sleep of 5 s comes first, so the Service has removed the pod before uvicorn stops accepting and no new call reaches a pod that is going away. The second section of the evidence file shows the stop with the M5 images.
